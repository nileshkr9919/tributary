# Review of the Tributary design, 2026-10-19

Reviews revision 1 of the spec (later revisions are in the changelog).
[2026-10-19-unified-messaging-platform-design.md](2026-10-19-unified-messaging-platform-design.md).

Three independent reads were merged and deduplicated: the designer's own read, a
distributed-systems correctness review, and a product and research-coverage review. Every
finding was checked against the spec text. Section numbers refer to the spec.

**Verdict: not ready to approve.** The core idea holds up: one replicated log, with consumer
behaviour chosen through profiles. But seven blockers change the M1 on-disk format or the wire
protocol. If they are deferred, M3 becomes a rewrite.

## Blockers: they change M1's storage or protocol

| # | Finding | Failure scenario | Fix |
| --- | --- | --- | --- |
| B1 | **The replicated log is treated as topic storage** (6.1, 6.4, 6.5). Many topic-shards and subscription-state records share one Raft log, which can only be trimmed from the front. | A 1-hour topic shares a group with a 365-day topic, so neither can free disk. Catch-up reads of one shard skip through other shards' interleaved records. | Use the Raft log only as a write-ahead log. Apply committed entries to per-topic-shard segments and a separate subscription-state store. Snapshot and truncate the log on its own schedule. Build M1's engine with this split. |
| B2 | **Acks and leases are not fenced** (5.2, 5.6, 5.8, 6.4). Nothing ties an ack to a specific delivery attempt. | A's lease expires and the message goes to B. A's late ack is accepted, so the key's next message dispatches while B is still working, breaking per-key ordering. Under exactly-once, both transactions commit. | Every delivery carries a lease token (shard, offset, attempt, epoch). Reject acks, extends and transactional acks with a stale token. Re-arm leases after failover rather than trusting wall clocks. |
| B3 | **Idempotency cannot guarantee one append per key** (5.1, 4.2, 8.1). The table is per topic, but appends happen per shard in different groups. | A keyless retry goes round-robin to a different shard and is appended twice. After a split, a retry reaches a child with no record of the key. At 100k msg/s a 24 h window is about 8.6 billion entries. Section 8.1 also says keys are generated "on produce retries", when they must exist before the first attempt. | Keep the dedup entry in the same group and the same log entry as the append. Route keyless records by hashing the idempotency key. Carry entries across splits. Consider producer ID plus per-shard sequence numbers, which bound state per producer. Fix 8.1. |
| B4 | **One stalled consumer can stop every producer** (6.5, 5.6, 5.2). Consumer-aware retention keeps whatever an abandoned durable subscription, broadcast member or held key still owes, and the hard cap then refuses produce. Ack and lease records also consume storage, so acks may be refused at the cap. | A forgotten test subscription, or one held payment key, fills the cap and blocks the topic. This is RabbitMQ's global memory alarm again, scoped to one topic. Consumers then cannot ack to free space, which deadlocks. | Per-subscription `backlog` limits (`max_age`, `max_bytes`) with `on_overflow` options (dead-letter, skip for this subscription, suspend, block producers). Default to anything except blocking producers. Add an inactivity TTL for durable subscriptions and members. Give state records their own reserve outside the cap. Report which subscription or key is pinning storage. |
| B5 | **Different ack levels share replication groups** (5.1, 6.1, 6.2). `none` and `leader` topics can sit in the same Raft group as `quorum` topics. | A follower acks an unsynced entry and loses power. It comes back with a shorter log, votes, and committed quorum records for other topics are overwritten. | Make the fsync rule a property of the group and place topics only in groups with a matching level. Or say followers always fsync, and fix the `ephemeral` profile's "no fsync". |
| B6 | **Exactly-once has no read isolation, and the M2 design will not survive M3** (5.4, 9). Nothing stops consumers from seeing a transaction's outputs before it commits. In a cluster, inputs and outputs almost always sit in different groups, so two-phase commit is the normal path. | A downstream subscription consumes the output of an aborted transaction. The coordinator-less M2 implementation is rebuilt in M3. | Specify the transaction log, commit and abort markers, and read-committed dispatch with a last stable offset per shard. Build the coordinator abstraction in M2, running on one node. |
| B7 | **Nothing is production-grade until M3, and formats are not versioned** (9, 10). The owner wants real users, but M1 and M2 run on one node with no high availability. No milestone commits to keeping the on-disk format or protocol compatible. | Data written in M1 may not survive the move to multiplexed groups in M3. Users repeat Kafka's and RabbitMQ's upgrade pain. | Version segment, state-record and protocol formats from M1, with a tested upgrade path. Either move replication ahead of most M2 features, or label M1 and M2 as not for production. |

## Major

| # | Finding | Fix |
| --- | --- | --- |
| J1 | **"Memory proportional to in-flight" is false** (6.4, 5.6, 4.3). Delayed messages need a not-before entry each, so 100M messages delayed a day means 100M entries. Per-key ordering must skip past a busy key's backlog, so it needs a per-key index or rescans the log. Acked ranges fragment once per message of a held key. | A durable, timer-ordered delay index on disk. A per-key pending index with bounded lookahead. State the real memory bounds. |
| J2 | **Split lineage conflicts with held keys** (4.2 vs 5.6). Children wait for the whole parent, so one held message stalls every key after a split. | Gate children per key or hash range: a child dispatches a key once the parent has nothing pending for that key. |
| J3 | **Compatibility rules miss broken combinations** (5.2, 5.3). Accepted but undefined: cumulative ack with delays, nack, retry or dead-letter; broadcast with per-shard ordering; webhook with broadcast or exclusive; exactly-once with webhook; exactly-once on a topic with ack `none`; filters with cumulative ack; delay beyond retention; keyless messages under per-key ordering; webhook batching. The exactly-once rule ("per-message or cumulative") rejects nothing. `exactly-once-pipeline` is a built-in in M1 although exactly-once ships in M2. | Add each pairing to the rule table with explicit semantics and tests. Mark which built-in profiles exist in which milestone. |
| J4 | **`event-stream` is not Kafka consumer-group behaviour** (5.3, 5.2, 6.4). It uses `exclusive`, which section 5.2 defines as one active member for the whole subscription. Section 6.4 treats exclusive as per shard. | Define it as shared, per-shard ordering, cumulative ack, with server-assigned shards. State that `exclusive` means whole-subscription failover. |
| J5 | **Corruption repair does not fit Raft** (6.3). Raft votes per node, not per range. A replica with a corrupt middle entry can still win an election, and leaders never fetch entries from followers. | Adopt protocol-aware recovery (the CTRL paper, FAST 2018): a corrupted node cannot campaign until it is repaired from a quorum. Model-check the change. |
| J6 | **Cost and ordering of state writes are unspecified** (6.4, 5.4). Every lease, ack and nack is a replicated write, multiplied by member count under broadcast. At-most-once avoids duplicates only if the "delivered" mark commits before dispatch. | Define which transitions must commit before an external effect (the at-most-once mark, transactional ack) and which can be batched (lease grants under at-least-once). Batch state records under group commit. |
| J7 | **Exit bars would pass a broken system** (9). "Every legal combination" is thousands of combinations multiplied by behaviours. The fault filesystem does not drop unsynced directory entries or renames, or produce torn writes, so a missing directory fsync passes. The memory bar ignores delayed, retrying, held-key and idempotency state. The linearizability model is undefined. | Use per-axis rules plus pairwise coverage and an explicit list of risky combinations. Make the fault filesystem model directory metadata, torn writes and fsync errors. Add delay, held-key and idempotency workloads to the memory bar. Define the consumer-history model for the fault suite. |
| J8 | **Lookup by ID cannot be fast, and "acked at" cannot be answered** (7.4, 6.4). A time-sortable ID carries no location. Ack state is compacted into ranges with no timestamps. | Encode the group or shard and offset in the ID, or keep a global ID index with stated retention. Drop "acked at", or keep a bounded history. |
| J9 | **Profile changes are unsafe by default** (5.3). Following the latest version means one edit, or a release that changes a built-in, silently changes retry and dead-letter behaviour everywhere. The refusal list omits guarantee, lifetime, delivery, filter and dead-letter target. Changes to a parent can make a child profile illegal. | Pin the version when a subscription is created, and roll out with an explicit command. Make built-ins immutable and versioned per release. Validate the whole `extends` tree and every subscription using it before applying. Extend the refusal list. |
| J10 | **Webhook delivery allows server-side request forgery** (5.2, 5.5). Tenants can point the broker at internal addresses, including the cloud metadata service at 169.254.169.254. | Deny private and link-local ranges by default, re-checking after DNS resolution. Add an allowlist per namespace. Support two signing secrets during rotation. |
| J11 | **Clients, gateway parity and migration come too late** (8.1, 9). Only a Go client until M5. The HTTP gateway lacks nack, extend, seek and push. There is no Kafka gateway, AMQP or MQTT until M5, and no import or mirroring tools. The research says ecosystem gravity, not architecture, is what sank Pulsar. | Give the HTTP gateway full parity in M1, with push over SSE or WebSocket. Ship Python and TypeScript clients by M2. Bring a Kafka produce and fetch subset, plus Kafka and SQS import, forward to M3. |
| J12 | **Expected consumer settings are missing** (5.2). No handler concurrency, ack batching, batch handlers or per-subscription rate limit. The spec never says whether a lease expiry counts as an attempt, so a message that crashes its consumer may loop forever. | Add `concurrency`, `ack_flush`, `handler_batch` and `rate_limit`. Count lease expiry as an attempt, and quarantine a message after N consecutive expiries. |
| J13 | **The built-in catalogue misses common patterns** (5.3). No request-reply and no recurring schedules. `durable-pubsub` uses broadcast, so a consuming service cannot scale out. The usual fan-out pattern, one work-sharing subscription per service, has no profile. `pubsub` overlaps with `fire-and-forget`. | Add `rpc` and `scheduled` profiles. Document fan-out as one `work-queue` subscription per service. Reserve broadcast for cases where every instance must see every message. |
| J14 | **Dead-letter requeue and retention are ambiguous** (5.7). Requeue as a re-append would duplicate the message to every other subscription. Dead-letter topics have no subscription, so consumer-aware retention does not protect them and they expire after 7 days. | Requeue as a per-subscription redelivery record that points at the dead-letter offset. Disable time-based deletion on dead-letter topics by default and alert on age. |
| J15 | **The producer side is under-specified** (5.1, 8.1). It never covers compression, batching and linger settings, a per-produce ack override, partial-batch failure, ordering under pipelined retries, topic auto-create, a maximum `deliver_at` horizon, or produce-only transactions. | Add a producer section covering all of these. |
| J16 | **Outbox and crypto-shredding are too late** (3, 9). Transactional enqueue is the main reason teams choose Postgres queues, and it arrives in M5. Data written unencrypted in M1 to M4 can never be shredded. | Ship an outbox relay or a prepare-and-confirm produce API in M2. Reserve a per-record encryption key-ID field in the M1 format. |
| J17 | **Section 3 promises fixes that arrive late** (3, 4.2, 9). "Partition count is a permanent guess" is listed as solved, but splitting arrives in M3. M1 says "fixed count" without saying who chooses it, which contradicts "users never set a shard count". | Tag each section 3 row with its milestone. Specify the M1 shard count and its default. |

## Minor

- **Two owners for offset assignment** (6.5 vs 6.1). The `object` storage class says the metadata quorum assigns offsets. Keep the data group as the only sequencer for every storage class.
- **Timestamps can go backwards after failover** (4.3, 5.8, 6.2). Assign `produced_at` as the maximum of the previous value and now, per shard, and replicate it. Lease, delay and TTL deadlines should be durations re-armed on failover, not wall-clock comparisons.
- **Hot keys are not handled** (4.2, 5.6). Splitting a hash range cannot split one key. Add per-key throughput and stall metrics. Allow key salting when ordering is `none`.
- **Overlapping settings and surprising defaults** (5.2). Three settings overlap: `ttl handling`, `on_exhausted` and `dead_letter`; merge them into one failure-outcome block. `start: latest` makes a producer-first deploy silently lose messages for `work-queue`. The default retry can park an ordered key for about an hour.
- **Follower fetch helps only cursor-style subscriptions** (6.6). Per-message dispatch runs on the shard leader, so zone savings for queue-style subscriptions are smaller than section 3 implies. State this.
