# Tributary: one log, every consumption model

Design document, 2026-10-19, revision 5 (adds AI workloads). Status: **not ready for planning**;
see [the revision 5 review](2026-10-19-unified-messaging-platform-review-r5.md). Earlier findings
are in [the first review](2026-10-19-unified-messaging-platform-review.md). Section 14 maps each finding and each AI requirement to the section
that resolves it. Research behind the design is in
[docs/research](../../research/README.md).

## 1. Intent

The owner asked for one platform that addresses the pain points of today's streaming platforms
and message queues in a single tool, for real users in production. The research found that most
of those pains come from one structural split and a handful of unsafe defaults, not from missing
features:

- **Logs and queues are separate systems.** A log (Kafka, Kinesis, Pulsar storage) is durable and
  replayable but cannot ack, retry, delay or dead-letter one message. A queue (SQS, RabbitMQ,
  Postgres) has those ergonomics but cannot replay or fan out cheaply. Nearly every team runs both,
  and every vendor is now bolting the missing half onto its product (Kafka share groups, RabbitMQ
  streams, Pulsar subscription types). The bolt-ons ship with feature matrices that differ by mode.
- **Defaults lose data or need a team.** Acks before fsync (NATS), partition-handling strategies
  that drop acked writes (RabbitMQ), single-AZ write-ahead windows (S3-native Kafkas), JVM and
  memory tuning, three or four stateful tiers (Pulsar), ZooKeeper-era metadata.

So the core idea is: **store every message once, in a replicated log, and let each consumer
decide how it receives it.** Push or pull, competing consumers or broadcast, at-most-once,
at-least-once or exactly-once, cumulative or per-message acks, ordering, concurrency, rate,
retry, dead-letter and backlog policy are all per-subscription settings, bundled into reusable
**profiles**. Queue, stream and pub-sub stop being product types and become profiles on the same
log. Everything else in this document is in service of making that core safe by default and
boring to operate.

**Built for AI-era workloads.** Model calls, agents and AI data pipelines are now a large share of
what flows through queues and streams, and they break assumptions older platforms were built on.
Provider limits are in tokens and money, not messages. Interactive and bulk requests compete for
the same quota. Agent runs last minutes, get superseded by the user's next message, and repeat
paid calls when retried from scratch. Deletes must reach vector stores, and regulators require
records of what happened. Section 5.14 and section 7.6 answer these with dispatch controls,
quota pools, cancellation, checkpoints, token streams, agent protocols and governance features,
all built on the same log and profile model.

### Success, in the owner's terms

A developer can replace "Kafka plus SQS (or RabbitMQ) plus a schema registry plus a hand-rolled
DLQ" with one binary, keep the semantics they relied on, and never lose an acknowledged message
under the default configuration.

## 2. Goals, non-goals, anti-goals

### Goals

1. **Consumer-oriented.** One topic serves any number of subscriptions. Each subscription chooses
   its delivery model, distribution, guarantee, ack model, ordering, concurrency, rate, failure
   handling, backlog policy, start position and lifetime (section 5.3).
2. **Profiles.** Those choices are bundled into named, versioned, inheritable profiles, with
   immutable built-in profiles for the common patterns and custom ones per namespace (5.4).
3. **Acknowledged means durable.** A produce ack is sent only after the record is fsynced on a
   quorum. Weaker ack levels are explicit per-topic opt-ins with their loss window stated. The
   replication protocol's own fsync rule never weakens in replicated groups (6.2). Memory groups,
   used only by ephemeral topics, are isolated from them and still persist election state (6.1).
4. **One binary.** Broker, metadata, schema registry, admin API and metrics in a single static
   binary. Local development runs the same binary with the same semantics.
5. **No permanent shard decisions.** Shards split automatically from M4. Before M4 a topic's
   shard count is fixed at creation with a default of 4, and section 3 says so.
6. **Every message is findable.** Look up any message by ID and see its state in every
   subscription; backlog is reported as message age, not only depth.
7. **No consumer can stop producers by accident.** Abandoned or stalled subscriptions are bounded
   by backlog limits and inactivity expiry (5.10).
8. **Cost is visible.** Bytes in, out, stored and cross-zone are metered per topic and namespace.
9. **Upgrades are boring.** Every on-disk and wire format is versioned from M1, and each release
   reads the previous release's data (6.9).
10. **Open governance.** Apache-2.0, no feature gated behind a source-available licence.
11. **AI-native dispatch.** Priority with ageing, fairness across tenants, token- and cost-based
    quota pools, back-pressure from model providers, supersede and cancel, progress checkpoints,
    resumable token streams and agent protocol support (5.14).
12. **Governed data.** Keyed deletes that reach every copy, erasure receipts, field-level access,
    gated topics and an audit log fit for AI record-keeping rules (7.6).

### Non-goals (for this design; may come later)

- Stream processing (Kafka Streams or Flink equivalents) and a connector framework.
- Multi-region replication. All replicas live in one region.
- A workflow engine. Step journaling with deterministic replay, workflow versioning, sagas and
  agent memory belong to engines such as Temporal or Restate; Tributary integrates with them
  (5.14.12).
- A hosted service, billing, or a web console beyond a minimal admin page.
- End-to-end exactly-once into external systems. The platform provides exactly-once processing
  inside itself and an inbox helper for external side effects (5.6).

### Anti-goals: failure even if it technically works

- Losing an acknowledged message under the default configuration, in any tested fault.
- A shared feature (seek, replay, filters, lookup, metrics, schema) that behaves differently under
  different subscription settings, or a combination of settings that is accepted but undefined.
  Illegal combinations are rejected at create time with a clear message (5.3).
- One stalled, abandoned or misconfigured consumer blocking producers, unless an operator
  explicitly chose that behaviour.
- Requiring a second system to run it: no ZooKeeper, etcd, Postgres, or separate registry.
- Exposing internal shards or capacity units as something users must pay for while idle.
- A profile edit or a platform upgrade silently changing how live subscriptions behave.
- One tenant, one runaway agent or one retry loop exhausting a shared model quota or budget for
  everyone else.
- Unreproducible performance claims. Every published number ships with the harness and config.
- Calling anything "Kafka compatible" without a published compatibility matrix.

## 4. Data model

### 4.1 Hierarchy

`namespace / topic / shard`, with subscriptions attached to topics.

- **Namespace**: the tenancy unit. Owns quotas, auth scopes, metering, custom profiles and
  egress rules for webhooks.
- **Topic**: a named log. Its behaviour comes from a topic profile (5.4): ack level, retention,
  storage class, group class, shard count, hard cap, maximum message size, maximum delay,
  idempotency window, schema compatibility mode.
- **Shard**: a unit of ordering and placement. Each shard owns a contiguous range of a 64-bit key
  hash space and has a stable 64-bit topic-shard ID.
- **Subscription**: a named consumer of a topic, with settings from a subscription profile plus
  inline overrides (5.3, 5.4).
- **Profile**: a named, versioned bundle of subscription or topic settings (5.4).
- **Schedule**: a named recurring message template (5.11).

### 4.2 Shards and splitting

- Records with a key are routed by hashing the key. Records without a key but with an idempotency
  key are routed by hashing the idempotency key, so a retry always reaches the same shard. Records
  with neither are spread across shards by the client in sticky batches.
- **Before M4**, the shard count is fixed when the topic is created. The topic profile sets it,
  default 4, maximum 256. It cannot change. Section 3 and the documentation state this plainly.
- **From M4**, a shard that exceeds a throughput or size threshold for a sustained window is
  **split** into two children with halves of its hash range. The parent is sealed: it takes no new
  writes but stays readable until retention removes it. Merging is a later candidate.
- **Lineage is gated per hash range, not per parent.** For each subscription, a child may
  dispatch a key once the parent has nothing pending for that key's hash. For per-shard ordering,
  the gate is the parent's cursor reaching the seal point for the child's range. A held key in
  the parent blocks only that key in the child, not the whole subscription.
- At a split, idempotency entries move with their hash range, and per-producer sequence state is
  copied to both children, each continuing from the parent's last sequence.
- A **position** is the set of per-shard offsets plus the lineage frontier. Clients see positions
  as opaque tokens. Time-based seek is always available.

## 5. Producing and consuming

The platform is consumer-oriented: a topic only stores messages, and each subscription chooses
how it receives them. Producing is covered first because several consumer guarantees depend on
it.

### 5.1 Fan-out

Every subscription on a topic receives every message (subject to its filter), independently,
with its own position and settings. This is pub-sub fan-out. **The recommended fan-out pattern is
one subscription per consuming service**, each with its own retry and dead-letter policy, and
work shared among that service's instances. `broadcast` distribution (5.3) is for the narrower
case where every instance must see every message, such as cache invalidation.

### 5.2 Producing

- **Producer sessions.** A client obtains a producer ID with an epoch from the cluster. Every
  batch carries the producer ID, epoch and a per-shard sequence number. The broker keeps the last
  sequence per producer per shard, rejects duplicates (acking them with the original IDs) and
  rejects gaps. This makes retries safe and keeps order under pipelined requests, with state
  proportional to active producers, not messages. It is on by default in every client. A
  session idle for 7 days (configurable per namespace) expires and its state is removed; a
  producer using an expired session is told to start a new one.
- **Application idempotency keys** are optional and cover a different case: the same business
  request sent twice, possibly by different processes. The deduplication entry is written in the
  same replicated log entry as the append, in the same data group as the shard, so check and
  append are atomic. The window is a topic setting, default 15 minutes, maximum 7 days. Entries
  live on disk and count against the namespace's storage quota, so the cost is visible.
- **Batches.** Clients batch with a linger time (default 5 ms) and size (default 1 MiB) and
  compress with zstd or lz4 (default zstd). The broker stores batches compressed. A batch is
  **atomic per shard**: either every record is appended or none is, and a rejection lists each
  failing record with its reason (for example a schema validation error at index 3). Clients
  split multi-shard batches and report results per shard.
- **Ack levels** come from the topic profile: `quorum` (default), `leader`, or `none`. A produce
  request may ask for a stronger level than the topic's, never a weaker one.
- **Delays**: `deliver_at` beyond the topic's maximum delay is rejected at produce time.
- **Topic auto-create** is off by default. A namespace may enable it with a named topic profile.
- **Producer transactions** (M3) append to several topics atomically, using the transaction
  machinery in 5.6. Readers never see uncommitted records.
- **Outbox relay** (M3): a built-in relay reads an outbox table in the application's Postgres
  database through logical replication and produces each row with its row ID as the idempotency
  key. It stores its Postgres replication position in metadata and confirms it to Postgres only
  after the produce is acknowledged, so a restart replays at most the rows between those two
  steps, and the idempotency key removes those duplicates. Teams keep transactional enqueue, the
  main reason they choose Postgres queues today.

**Compatibility rules.** The broker evaluates them against the subscription's effective settings
and its topic's profile at create time and on every change. A rejection names the conflicting
settings and suggests a fix.

| R6 | `exactly-once` requires `per-message` ack, `pull` or `push` delivery, and a topic in a `replicated` group with `quorum` acks; output topics must meet the same condition (checked when a transaction adds an output) | The transaction's guarantees rest on quorum durability and per-delivery tokens. Cumulative ack has no per-delivery token, so it is rejected. |
| R7 | `per-shard` with `delay: honour` is allowed and means a delayed or retrying head message blocks its shard | Strict order implies head-of-line blocking; the stuck report shows it. |
| R8 | `per-key` with `delay: honour` means a delayed message blocks only its key until due. Messages without a key have no ordering constraint under `per-key` | Defines the two cases that were previously undefined. |
| R9 | `filter` with `cumulative` ack: filtered-out messages are passed over by the cursor | Defines the previously undefined case. |
| R10 | `ephemeral` lifetime excludes `backlog.on_overflow: block-producers` | An ephemeral listener must never hold up producers. |
| R11 | `block-producers` requires the namespace flag `allow_block_producers` | Makes the RabbitMQ-style stop an explicit operator choice. |
| R12 | A subscription's `backlog.max_age` may not exceed its topic's retention | The data would not exist. |
| R13 | A topic's maximum delay may not exceed its retention, and a subscription's longest back-off step may not exceed its topic's retention | A delayed or backed-off message would be deleted before it is due. |
| R14 | A subscription whose `backlog.on_overflow` is `dead-letter` must have `inactivity_ttl` shorter than `backlog.max_age` | Otherwise an abandoned subscription copies its whole backlog into a dead-letter topic before it is suspended. |
| R15 | Topics in a `memory` group must use ack level `none` | A memory group has no fsync, so any stronger ack would be untrue. |
| R16 | `priority`, `fairness`, `per_key` controls, `quota` corrections, `batch_window`, `sample` and `failure.on_reason` require `per-message` ack | They reorder, skip or regroup individual messages, which a cursor cannot express. |
| R17 | `per_key.on_arrival: supersede`, `per_key.debounce` and `per_key.coalesce` require `per-key` ordering and exclude `exactly-once`; `per_key.max_in_flight` above 1 requires `ordering: none` | They act on the one in-flight message per key; ordered keys allow only one. Supersede or coalesce could otherwise give a transactional input two terminal states. |
| R18 | With `per-key` ordering, priority and fairness choose among keys, never within a key | A high-priority message behind a lower-priority one for the same key waits, so key order holds. |
| R19 | Delete markers are never removed by `coalesce`, `sample`, `filter` or `deliver_if_changed` | Downstream copies must always learn of deletes. |
| R20 | Under `at-most-once`, quota pools charge the estimate only, and `failure.*` AI settings do not apply | There is no ack to report usage on. |
| R21 | `batch_window` requires `at-least-once` and a lease maximum at least as long as the park duration | Members must be redeliverable if the batch is lost. |
| R22 | `failure.on_reason` targets must be other topics, and routing counts toward the target topic's `max_hops` | Prevents routing loops. |
| R23 | A gate subscription must be durable, `at-least-once` and `per-message` | Approval must survive restarts and cover each record. |
| R24 | Tokens with the `shadow` scope may produce only to shadow topics | Shadow replay cannot cause production side effects. |

**Defaults are clamped; explicit values are checked.** Default values are adjusted to satisfy R12
to R14 for the subscription's topic: for example, on a 1-day topic the default `backlog.max_age`
is 1 day, the default `inactivity_ttl` is half of it, and default back-off steps stop at the
retention. Only values a user or profile sets explicitly are rejected.

The conformance suite tests both sides of every rule, every pair of values across the axes
(pairwise coverage), and an explicit list of high-risk combinations kept in the repository. It
does not attempt the full cross-product.

**Shared behaviour is identical across combinations.** Seek, replay, filters, lookup, metrics and
schema validation work the same way whatever the settings.

**Custom profiles** are defined per namespace and may `extend` another profile and override any
settings:

```yaml
kind: subscription-profile
name: payments-jobs
extends: ordered-work-queue@1
failure:
  max_attempts: 5
  backoff: [1s, 30s, 5m, 30m]
  on_exhausted: hold
lease: { initial: 2m }
backlog: { max_age: 3d, on_overflow: dead-letter }
```

**Using profiles.** A subscription names a profile version and may override settings inline. The
effective settings are the profile chain, then the overrides. `trib sub show` prints the
effective result and where each value came from.

**Changing profiles safely.**

- A subscription **pins** the profile version it was created with. Editing a custom profile
  creates a new version; nothing changes for existing subscriptions until an operator upgrades
  them with `trib sub upgrade <sub> --to <version>`, or upgrades many with
  `trib profile rollout <profile> --to <version>`.
- Every upgrade shows a dry run first: affected subscriptions, setting differences, and any
  compatibility-rule failures. Validation covers the whole `extends` tree and every subscription
  that would use the new version.
- Changes to `guarantee`, `ack`, `ordering`, `distribution`, `delivery` or `lifetime` alter the
  meaning of stored state, so they are refused for live subscriptions; the operator creates a new
  subscription and moves consumers. Changes to `filter` or the dead-letter target are allowed
  only with an explicit flag, because they change which messages are owed or where failures go;
  existing dead letters stay where they are.
- **Topic profiles follow the same rules**: topics pin a version and are upgraded explicitly with
  a dry run. A change that would break a compatibility rule for any live subscription on the
  topic is refused. Shrinking retention requires an explicit flag, and the dry run reports how
  much owed data would be released and for which subscriptions.
- **Where profiles live**: in metadata, managed by API, CLI or YAML applied with `trib apply`, so
  they can be kept in Git and reviewed.
- **Clients follow the effective settings.** A client attaching to a subscription receives them
  and configures its concurrency, batching, credits, ack flushing and lease extension, so
  behaviour never depends on per-language client defaults.

### 5.5 Delivery tokens and fencing

Every delivery carries a **delivery token**: topic-shard ID, offset, attempt number, and the
**epoch** of that subscription on that shard. The epoch is kept per subscription per shard, in
the shard's data group, so it needs no coordination across groups. Acks, nacks, lease extensions and transactional acks must
present the token.

- The broker rejects any token whose attempt is not the current attempt for that message, or
  whose epoch is stale. A consumer whose lease expired cannot ack after the message has gone to
  someone else; it receives a "lease lost" error and must not commit side effects that depend on
  the ack.
- A shard's epoch increases when that shard's assignment changes (per-shard ordering, exclusive
  failover), on a seek, and when its data group elects a new leader. Each of those invalidates
  outstanding tokens for that shard only, so a stale active member or an ack that crosses a seek
  is rejected. The new epoch is committed before the first dispatch that uses it.
- **Durable leases survive leader changes.** A lease is durable when the subscription sets
  `lease.durable: true`, when its maximum total exceeds 5 minutes, or when it covers a batch
  (5.14.8). A durable lease is committed before its token is handed out, and its token carries a
  lease ID. A leader election does not invalidate durable leases: the new leader re-arms them
  from the state store. Assignment changes and seeks still invalidate them. So a six-hour agent
  run or a parked provider batch keeps its lease across a rolling upgrade.
- Lease, delay, back-off and TTL deadlines are stored as durations from a replicated reference
  point and re-armed by a new leader from its own monotonic clock. Clock skew between nodes
  cannot expire a lease early.

### 5.6 Delivery guarantees, stated precisely

**When state must be durable.** The table says which state changes must be committed before the
broker does something visible.

| Transition | Rule |
| --- | --- |
| At-most-once dispatch | The "delivered" mark is committed before the message is sent, one commit per dispatch batch (per member under broadcast). A failover cannot resend it. On `memory` group topics the mark is kept in memory, because the data itself does not survive a restart. |
| At-least-once lease grant | Short leases may be batched and need not be durable before sending; after failover, the epoch increase invalidates them and the messages are redelivered, and the attempt count may undercount by one per failover. Durable leases (5.5) are committed before the token is sent and survive leader changes. |
| Ack, nack, extend | Committed before the success response. Clients batch acks with `ack_flush`. |
| Cumulative commit | Committed before the success response. |
| Transactional ack | Committed through the transaction coordinator before the response. |

State records are batched under group commit with produce traffic, so the cost is amortised
fsyncs, not one per message.

**At-most-once**: no duplicates from the broker. A consumer crash loses the message.

**At-least-once**: redelivered until acked, dead-lettered, dropped by policy, or skipped by a
backlog policy. Duplicates are possible after a lease loss. Every delivery carries the stable
message `id` and attempt number.

**Exactly-once** means **exactly-once processing inside the platform** (M3):

- A consumer opens a transaction with the namespace's **transaction coordinator**, a replicated
  state machine hosted in a data group. Inside the transaction it acks input deliveries (with
  their tokens) and produces output records to any topics.
- Output records are appended immediately but marked with the transaction ID. Every shard tracks
  a **last stable offset**: the first offset belonging to a transaction that is still open.
  Subscriptions never dispatch past it, so no reader sees uncommitted output.
- Commit is two-phase. In the prepare phase each participant shard validates the input tokens
  (a lost lease aborts the transaction) and writes a durable **prepared-ack** record for each
  input. A prepared input is removed from dispatch, lease expiry and redelivery until the
  decision, and prepared state survives epoch changes and failover, so no second transaction can
  take the same input. The coordinator then writes the decision, and each participant writes a
  commit or abort marker. On abort, prepared inputs return to dispatch with their attempt count
  increased. Aborted records are skipped by every reader.
- Idempotency entries and producer sequence advances made inside a transaction take effect only
  when its commit marker is applied. On abort they are discarded, so a retry in a new transaction
  is appended normally, not mistaken for a duplicate.
- **Transactions must be short.** The open-transaction timeout defaults to 60 seconds, maximum 15
  minutes; an expired transaction aborts. While a transaction is open, every subscription on the
  affected shards waits at the last stable offset, so the oldest open transaction is a metric
  with an alert, and the stuck report names it.
- The coordinator is built once, in M3, on the replicated cluster. It runs the same way on a
  single node, so there is no single-node design to replace later.
- Side effects outside the platform are not covered. Each client ships an **inbox helper**: a
  small table in the consumer's own database keyed by message `id`, written in the same database
  transaction as the side effect. The documentation states this boundary on the first page about
  guarantees.

### 5.7 Delivery models

- **Pull**: the consumer requests up to `batch_size` messages and may long-poll. The default,
  because it is the easiest to reason about and works behind load balancers.
- **Push over a connection**: the consumer opens a streaming connection and grants credits. The
  broker sends while credits remain; the client returns credits as handlers finish. A slow
  consumer can never be flooded. HTTP clients get push over Server-Sent Events.
- **Webhook** (M3): a delivery worker POSTs each message, or a batch when enabled, with an HMAC
  signature over the body and timestamp, the message `id`, attempt and headers.
  - A 2xx acks. For batches, a 2xx with a JSON body listing failed IDs nacks only those; a 2xx
    without that list acks the whole batch; any other outcome applies to the whole batch.
  - Configured retryable statuses and timeouts count as failed attempts. Other statuses count as
    a nack, with the response body recorded as the failure reason.
  - Per-endpoint concurrency and a circuit breaker protect the receiver. An open circuit pauses
    delivery without consuming attempts.
  - **Egress guard**: the broker refuses private, loopback, link-local and cloud metadata
    addresses (including 169.254.169.254) by default. It checks after DNS resolution and pins the
    resolved address for the request, so DNS rebinding cannot bypass it. Namespaces may add an
    explicit allowlist; only operators may permit private ranges. Redirects are not followed.
  - Two signing secrets may be active at once so secrets rotate without downtime.

### 5.8 Per-key ordering

At most one message per key is in flight per subscription (per member, under broadcast). The
next message for a key is dispatched only after the previous one is acked, dead-lettered, dropped
or skipped.

- **Per-key index.** When any subscription on a topic uses per-key ordering, each shard keeps an
  on-disk index of `(key, offset)` for its retained records. It is written once per record,
  whatever the number of subscriptions, and its size is proportional to retained records, on
  disk.
- **Dispatch without rescans.** Each per-key subscription (each member under broadcast) has a
  dispatch frontier that only moves forward through the log. When it reaches a record whose key
  is busy (in flight, retrying, delayed or held), it skips the record and notes that the key has
  more pending. When the key frees, the dispatcher finds the key's next record with a range scan
  on the index from the key's last dispatched offset. Per-subscription memory is bounded by keys
  that are busy, not by backlog.
- If a key's head message is retrying or delayed, only that key waits. When it is dead-lettered
  or dropped, the key resumes and the subscription records that the key skipped a message. With
  `on_exhausted: hold`, the key stays parked until an operator requeues, skips or deletes the held
  message; other keys are unaffected.
- **Hot keys.** Metrics report per-key throughput, in-flight time and stall time for the top keys.
  From M4, a topic with `ordering` not required by any subscription may enable **key salting**,
  which spreads a hot key across a configured number of sub-keys.

### 5.9 Dead letters and requeue

- Dead-letter topics use the `dead-letter` topic profile: **no time-based deletion**, a size cap
  with an alert, and an alert when the oldest dead letter passes 7 days. Dead letters always have
  an owner signal.
- Each dead letter is a copy of the original with `trib-failure-reason`, `trib-attempts`,
  `trib-first-failed-at`, `trib-last-failed-at`, `trib-source` (topic, shard, offset, id),
  `trib-operation-id` and the last progress checkpoint. A copy is needed because the source may
  expire.
- **Requeue** writes a **redelivery record** to the source subscription's state, pointing at the
  dead-letter offset, with a fresh attempt count. The redelivery keeps the original operation ID
  and progress checkpoint, unless the operator asks to reset progress, so effect keys and step
  results still apply. It does not append to the source topic, so
  other subscriptions never see a duplicate. Requeue works by ID list or by filter.
- Dead-letter appends are rate-limited and use the storage reserve in 6.6. If a dead-letter topic
  reaches its cap or the reserve runs out, dead-lettering falls back to `skip` for that
  subscription, records the skipped range, and raises a critical alert, so a full dead-letter
  topic can never block the source topic.

### 5.10 Backlog limits, inactivity and storage pinning

- A durable subscription owes messages up to its `backlog.max_age` and `backlog.max_bytes`.
  Messages that cross the limit follow `backlog.on_overflow` (5.3). The default never blocks
  producers.
- A subscription or named broadcast member with no consumer and no ack for `inactivity_ttl` is
  **suspended**: it stops pinning storage, raises an alert, and can be resumed later with the gap
  recorded and visible.
- **Cap pressure.** When a topic or namespace reaches 90 percent of its hard cap, the broker
  applies `backlog.on_overflow` early, oldest data first, to the subscriptions pinning the oldest
  segments, including messages waiting behind held keys, and alerts. Producers are refused only
  if the cap is still reached after that, which means it is full of data no policy may release:
  messages in flight, held messages themselves, open transactions, or subscriptions that chose
  `block-producers`. The pinning report names them.
- **Storage-pinning report**: `trib storage pinning <topic>` lists which subscriptions, members,
  held keys and open transactions are keeping each segment alive, with sizes.

### 5.11 Request-reply and schedules

- **Request-reply** (M3): a client creates an inbox topic with the `rpc-inbox` profile and an
  ephemeral subscription on it. It produces requests with `reply_to` set to the inbox and a
  `correlation_id`. Handlers on an `rpc` subscription reply by producing to `reply_to` with the
  same `correlation_id`, and the client library matches responses and enforces a timeout.
- **Schedules** (M3): a schedule is a metadata object with a cron expression or interval, a
  time zone, a target topic and a message template. The metadata leader fires each occurrence by
  producing with idempotency key `schedule-id + occurrence-time`, then records the occurrence as
  the schedule's last fired time in metadata. A new leader resumes after the recorded time, so at
  most the single occurrence in flight during a failover can be fired again, and its idempotency
  key removes the duplicate unless the failover outlasts the topic's idempotency window. Missed
  occurrences during downtime follow a per-schedule policy: `fire-once`, `fire-all` or `skip`.

### 5.12 Seek and replay

Any subscription can be moved to an offset, a timestamp, or the earliest or latest record. For
per-message ack, moving backwards marks everything after the new point as unacked again. A seek
increases the subscription epoch, so in-flight tokens are invalidated (5.5). Replay into a new
subscription never disturbs live subscriptions.

### 5.13 Wildcard topics

Topic names are dot-separated. Wildcard subscriptions across many topics (NATS-style `orders.*`)
are deferred because they complicate ordering and exactly-once. Filters within one topic cover
the common routing cases meanwhile.

### 5.14 AI workloads

Model calls, agents and AI data pipelines put new demands on a message platform. Three research
reports cover them: [inference traffic](../../research/ai-inference-traffic.md),
[agents](../../research/ai-agents.md) and
[data pipelines and governance](../../research/ai-data-pipelines.md). Their requirements carry
the IDs I1 to I16, A1 to A20 and D1 to D18; section 14.2 maps each one to this design. Everything
here is expressed as subscription settings, topic settings, profiles or a small number of new
primitives, so it works with every delivery model and guarantee that the compatibility rules
allow.

#### 5.14.1 Dispatch indexes

Priority, fairness and per-key controls all need the dispatcher to find the next eligible record
without rescanning the log. They share one mechanism, extending the per-key index of 5.8.

- A topic maintains on-disk **dispatch indexes** in the state store, written once per record
  whatever the number of subscriptions:
  - a **key index** of `(key, offset)` when any subscription uses per-key controls or key reads;
  - one **composite index** per distinct dimension tuple that its subscriptions declare, for
    example `(priority band, fairness value, offset)` for `llm-requests`. A subscription's
    dispatcher finds "the next record in band B for tenant T" with one range scan, and checks the
    key against its busy set, so it never intersects separate indexes or rescans.
- Each subscription keeps a forward-only frontier per active tuple and per busy key. Frontiers,
  debounce timers, per-key quota buckets and budget counters are held in the state store with an
  in-memory cache of fixed size, so resident memory is bounded by the cache sizes, not by
  backlog, tenants or keys (6.6).
- **Scope of priority and fairness.** Each shard leader orders dispatch for its shards. To serve a
  subscription as a whole, every leader publishes a summary of its band heads and their ages every
  100 milliseconds, and the broker node handling a receive request takes from the shard whose
  head ranks highest. Priority inversion across shards is therefore bounded by the summary
  interval plus one dispatch round, and the documentation states that bound.

#### 5.14.2 Priority and fairness

Priority was a non-goal in revision 1; AI traffic makes it necessary, because interactive
requests and bulk jobs share the same model quota (I5).

- **Priority bands.** A message may carry `trib-priority` with a band name. A subscription
  declares its bands in order with weights, for example `interactive: 8, standard: 2,
  background: 1`, a maximum wait per band, and `priority.max_total_wait`. The dispatcher serves
  bands by weight. **Ageing** promotes a message one band each time it has waited longer than
  its band's maximum wait. A message that has waited longer than `max_total_wait` enters the
  **overdue lane**, which is served before every band, oldest first, so a promoted message never
  queues behind an ever-growing top band.
- A redelivered or delayed message keeps its band, and its wait is measured from when it last
  became eligible: its original enqueue, its due time, or the end of its back-off.
- Under sustained overload no queue can bound every wait; the guarantee is that no message
  waits longer than `max_total_wait` plus one dispatch round while consumer capacity exceeds the
  arrival rate of overdue messages.
- **Fairness.** `fairness.key` names a header. From M2 the default is the server-stamped
  `trib-tenant` (7.6); in M1, the subscription must name the header.
  The dispatcher round-robins across fairness values with pending messages, optionally weighted,
  with `fairness.max_in_flight_per_value` capping any one value (I6, A3). A tenant with a million
  queued messages delays another tenant's first message by at most one dispatch round.
- Priority is applied first, then fairness within a band, then order within a key.

#### 5.14.3 Per-key controls

These extend per-key ordering for agent sessions, conversations and documents.

- **`per_key.max_in_flight`**: a concurrency cap per key without ordering, for example "at most
  two runs per user" (A3). Per-key ordering is the special case of 1 with order.
- **`per_key.on_arrival: supersede`**: a new message for a key whose previous message is in
  flight makes that delivery's next extend or ack return `superseded`, and push clients receive a
  cancel notice. The old message is marked superseded, never redelivered, and the new one is
  dispatched when the old lease ends (A1). This is how a user's new chat message cancels the run
  for their previous one. The shard leader checks the key's busy set when the new record is
  appended, so the notice goes out at append time, not when the dispatch frontier reaches the
  record.
- **`per_key.debounce`**: a key becomes eligible only after it has been quiet for the window
  (A2).
- **`per_key.coalesce`**: `none`; `latest` delivers only the newest pending record for the key
  and records the older ones as coalesced (D1); `batch` delivers all pending records for the key
  as one handler batch (A2). **Delete markers are never coalesced away**: if any pending record
  for the key is a delete marker, it is delivered before the latest record.
- **`per_key.quota`**: a rate per key, with `on_exceed: wait` (the key resumes automatically
  when the quota refills; the default) or `dead-letter` (A16).

#### 5.14.4 Quota pools, budgets and usage

Model providers limit tokens and spend, not messages, and the true cost of a call is only known
after it returns (I1, I2, D3, I13, I14, A18).

- A **quota pool** is a named object with a unit (`requests`, `tokens`, `cost`, `bytes` or a
  custom unit), a refill rate and burst, and optionally a parent pool. Pools nest, for example
  organisation, then project, then API key, and a child never exceeds its parent. Pools belong to
  a namespace; operators may create pools shared across namespaces, matching a provider account
  used by several teams.
- A subscription draws from one or more pools. At dispatch it is charged an **estimate**, taken
  from a header such as `x-est-tokens` or a default, multiplied by a **learned correction
  factor**: the subscription's recent ratio of actual to estimated usage. On ack, the consumer
  reports **actual usage** (tokens in, tokens out, cost, or any named numbers), and the pool is
  corrected; an overrun becomes debt that delays the next dispatch.
- `pool.max_outstanding` caps the estimated units in flight against a pool, which bounds how far
  actual usage can run ahead of corrections.
- **Pool priority** (D4): each subscription drawing on a pool has a `pool_priority`. When the
  pool is short, higher pool priorities are granted first, so a `backfill` subscription at the
  lowest pool priority uses only capacity the live subscriptions leave.
- **Budgets** are totals over a period (daily, monthly) on a pool or a fairness value. Reaching a
  budget **pauses** dispatch for that scope and raises an alert.
- **Paused is not suspended.** A scope paused by a budget, a `throttled` or `quota_exhausted`
  nack, or a kill switch keeps pinning its data, and its backlog overflow policy is not applied
  while paused, up to cap pressure (5.10). This is different from the inactivity suspension in
  5.10, which releases data. Creating a subscription warns when a budget period is longer than its
  `backlog.max_age`.
- **`failure.max_cost`** dead-letters a message whose reported usage summed over its attempts
  passes a cap, so a retry loop cannot overspend (I14).
- **Usage reporting** feeds metrics by subscription, pool and any configured header labels, such
  as tenant and feature (7.5).
- In a cluster, dispatchers on many shard leaders draw from a pool through a **pool
  coordinator** hosted in a data group. It grants units to dispatchers in small chunks with a
  time limit and records every grant in a **durable grant ledger**. A new coordinator after
  failover waits for outstanding chunk time limits to pass before granting again, so a failover
  never re-grants units already handed out.
- Usage corrections are written in the same commit as the ack at the shard leader and forwarded
  to the coordinator idempotently, by ack ID, so debt survives any failover.
- **The bound, stated precisely**: estimated units granted never exceed the pool plus one chunk
  per dispatcher; actual usage beyond estimates is limited by `max_outstanding` times the
  correction error, and is reported as overshoot and repaid as debt. A child pool's grants are
  drawn from its parent's, so a child never exceeds its parent.
- **Who may pause a pool.** A `throttled` or `quota_exhausted` nack with `scope: pool` takes
  effect only if the consumer's token has the `pool-admin` permission for that pool. Otherwise it
  is applied at subscription scope and an alert names the consumer, so one tenant cannot stop a
  pool shared with others. `retry_after` is capped by the pool's `max_pause`, default 15 minutes.

#### 5.14.5 Nack reasons and back-pressure

A plain nack counts an attempt. Model APIs fail in ways that should not (I3, I4, I7, A9).

| Nack reason | Effect |
| --- | --- |
| `retry` (default) | Counts an attempt and follows the back-off. |
| `throttled` with `retry_after` and a scope (`message`, `subscription`, `pool`, `key`) | Pauses that scope for the given time. **Does not count an attempt.** |
| `quota_exhausted` with a scope and optional resume time | Pauses the scope until an operator resumes it or the time passes, and alerts. Does not count an attempt. |
| `overloaded` | Counts an attempt and feeds fallback routing (5.14.8). |
| `permanent` | Applies `failure.on_exhausted` at once, with the reason recorded. |

- **No throttle loops.** `retry_after` has a minimum of 100 milliseconds. A message that has
  spent longer than `failure.max_throttled` (default 24 hours) in throttled pauses is treated as
  a failed attempt each time thereafter, so it eventually reaches `on_reason` or `on_exhausted`.
- **Saturation gate**: a subscription may name a signal, reported by consumers through the API or
  read from a metric endpoint, and a threshold. Dispatch stops within one second of the signal
  crossing the threshold and resumes when it falls.

#### 5.14.6 Cancellation and kill switches

- **Control channel.** Every connected member, pull or push, keeps a lightweight server-to-client
  control stream (a gRPC stream, or Server-Sent Events over HTTP). Cancel, supersede and pause
  notices travel on it and reach the holder within one second. Extends and acks also return the
  status, for clients that are briefly disconnected.
- **Cancel** by message ID, or by key within a subscription (I11, A4, A7). Pending and delayed
  deliveries are removed; an in-flight holder receives `cancelled` on the control channel. The
  reason is recorded and a cancelled message is never redelivered. If the message is a prepared
  input of an exactly-once transaction (5.6), the cancel takes effect only after the decision:
  a commit wins and the cancel is recorded as too late; an abort ends the message as cancelled.
- **Kill switch**: pause a subscription, a key, or every message with a given value of an
  indexed dimension (key, tenant, or a declared priority or fairness header) across the cluster
  (A17). A switch on another header first builds an index and reports `applying` until it is
  ready. Holders are told `paused` on the control channel so workers stop. Resuming is explicit.
- A kill switch is a metadata object. It is reported as applied only after every relevant shard
  leader has confirmed it. Leaders hold a metadata lease renewed every 250 milliseconds; a leader
  whose lease is more than one second old pauses new dispatch until it is renewed, so a
  partitioned leader cannot keep dispatching past a switch. This trades a short dispatch pause
  during metadata trouble for a hard stop guarantee; operators may relax the staleness bound.
- Kill switches are logged by the node in M1 and recorded in the audit log from M2 (7.6).

#### 5.14.7 Long-running work and effect keys

- **Long leases**: `lease.max_total` may be raised up to the topic's retention (A5).
- **Progress checkpoints**: an extend or a nack may carry up to 64 KiB of progress. The broker
  stores it in the subscription state and returns it on redelivery, with the attempt number and
  the previous holder (I8, A5). A crashed worker's successor resumes instead of restarting.
- **Operation ID and effect keys**: every delivery exposes an operation ID, which is the message
  `id`, or the original message's ID carried in `trib-operation-id` when a message was rerouted
  or requeued (I9). Clients provide `effect_key(step)`, a hash of the operation ID and a step
  name, to use as the idempotency key for model calls, payments and other external effects (A8).
  Webhooks send `Idempotency-Key` with the operation ID on every attempt.
- **Step helper**: clients provide `step(name, fn)`, which runs `fn` once per operation, stores
  small results in the progress checkpoint, and returns the stored result on later attempts. It
  is a convenience over checkpoints, not a workflow engine (5.14.12).

#### 5.14.8 Batching for provider batch APIs and fallback routing

- **Batch windows** (I12): `batch_window` groups messages by count, bytes or age into one
  delivery with a **batch token**. The holder may park the batch for up to 48 hours under one
  durable lease (5.5), which survives leader changes, so a parked batch is never resubmitted to
  the provider because of a failover. Any process holding the batch token, such as the webhook that receives a provider's
  batch-complete callback, may ack, nack or dead-letter individual members. The `provider-batch`
  profile packages this.
- **Fallback routing** (I16): `failure.on_reason` lists rules such as "after 3 `overloaded`
  nacks, or while the webhook circuit is open, route to topic `llm.fallback`". A routed message is
  copied to the target topic with `trib-operation-id`, its attempt history and `trib-routed-from`;
  the original's disposition is recorded as routed. Routing counts as a hop (5.14.10).

#### 5.14.9 Sampling, backfill and changed-field delivery

- **Sampling** (D7): `sample.fraction` with `sample.by` key or header makes a deterministic
  decision by hash, so a whole session is kept or dropped, and `sample.always` is a filter for
  records that are always delivered, such as errors. Delete markers are never sampled out.
- **Backfill** (D4): the `backfill` profile runs a second subscription from the earliest record
  or a time, at the lowest pool priority of the same quota pool, so it uses only capacity live
  traffic leaves. It skips, and records, records that expire before it reaches them instead of
  dead-lettering them. It reports progress, an ETA and a "caught up" event. Re-embedding millions of
  documents after a model change is this profile.
- **Changed-field delivery** (D5, M4): `deliver_if_changed` lists schema fields; a record is
  delivered only if one of them differs from the previous record for its key, using the latest
  value by key or a before-image from the outbox relay.

#### 5.14.10 Agent safety

- **Hop limit** (A15): a topic sets `max_hops`. Clients producing inside a handler set
  `trib-hops` to the incoming value plus one and `trib-causation-id` to the incoming ID
  automatically; the broker refuses or dead-letters records over the limit, so an agent loop
  A to B to A stops.
- **Trace pass-through** (A13): `traceparent`, `tracestate` and `baggage` are kept byte for byte,
  and the broker emits linked OpenTelemetry messaging spans. GenAI-specific attributes are not
  emitted until the OpenTelemetry GenAI conventions are stable.

#### 5.14.11 Token streams and key reads

- **Key reads** (A11, D18): read every record for one key from an offset, follow new records for
  that key live, or read the latest value for a key. Key reads return committed records only.
  Seek-by-key marks one key's records unacked for a subscription so only that key is replayed.
  Instead of increasing the shard epoch, it increases the attempt number of that key's in-flight
  messages, which fences only that key. All use the key dispatch index.
- **Token streams** (I10): the `token-stream` topic profile keys each model response by request
  ID, keeps it for minutes, and marks the end with `trib-end-of-stream`. Readers see committed
  chunks only. A client that disconnects reconnects by key and last offset and receives the rest
  exactly once; a second device can read the whole stream.
- The profile uses leader acks for latency, so the producing client keeps each chunk buffered
  until the broker reports it committed. If a leader change loses acknowledged chunks, the next
  append is rejected with the last committed sequence, and the client resends from there, so the
  stream is never truncated.
- **Fork a key** (A12, M3): copy a key's records up to an offset to a new key with
  `trib-forked-from`, for branching an agent conversation or rerunning it from a point.
- **Durable inbox** (A6): the `durable-inbox` topic profile is a replicated, quorum topic with up
  to 30 days of retention, for approvals and replies that must survive restarts.

#### 5.14.12 Where Tributary stops: workflow engines

Tributary owns **the unit of work and the wire between agents**: one message, its lease, retries,
per-key exclusivity, cancellation, timers, correlation, fair dispatch, quotas, tracing and audit.
It does not own **the code path inside a run**: step journaling with deterministic replay,
workflow versioning, compensation and sagas, run state beyond a progress checkpoint, and agent
memory. Those belong to workflow engines such as Temporal, Restate, DBOS and Inngest.

Rule of thumb: a run that fits in one lease and can resume from a checkpoint needs only
Tributary; many effectful steps or multi-day stateful waits need an engine.

Integration (M3): a subscription starts engine runs using the message ID as the run ID, so
redelivery is idempotent; replies and approvals arrive on topics and are delivered to the waiting
run by correlation key; runs emit step and audit events to topics. M3 ships documented patterns
and a reference integration for Temporal.

#### 5.14.13 Agent protocols

- **MCP server** (M3): Tributary exposes a Model Context Protocol server so agents can produce,
  receive, ack, look up messages and read keys as tools, scoped by the caller's token, with the
  same field-level restrictions as any other read (7.6).
- **A2A transport** (M3): the Agent2Agent protocol states that its streams are not a reliable
  delivery mechanism and makes webhook retries optional. Tributary can carry A2A tasks durably:
  task messages keyed by task ID, status updates on a topic by task key, reliable resume through
  key reads, and push notifications received through callback ingest.
- **Callback ingest** (A19, M3): an HTTPS endpoint per topic that verifies an HMAC signature or a
  JWT, deduplicates by a configured header used as the idempotency key, and produces to the topic.
  It is the entry point for provider batch callbacks, A2A push notifications and third-party
  webhooks.

## 6. Storage and replication

### 6.1 Topology

- One binary type. Each node runs the broker, a member of the **metadata Raft group** (on the
  first three or five nodes), and replicas of **data groups**. A single-node deployment (M1,
  `trib dev`) is the same design with groups of one.
- A **data group** is a Raft-replicated write-ahead log on three nodes by default, hosting many
  topic-shards. The number of groups grows with data volume, not with the number of topics,
  subscriptions or consumers. Groups split when they grow past a size or throughput threshold
  (M4).
- **Group classes.** `replicated` groups follow the full Raft fsync rule. `memory` groups keep
  their log in memory and lose data on restart; only topics with the `ephemeral` or `rpc-inbox`
  profile live there. The two classes are never mixed in one group, so a weak topic can never
  weaken a strong one.
- **Election state is always durable.** In every group class, Raft term, vote and membership are
  fsynced before they take effect. A restarted replica of a memory group rejoins as a non-voting
  learner under a new replica identity and becomes a voter only after catching up, so it can
  never vote twice in a term or elect a second leader.
- The metadata group holds namespaces, topics, profiles, subscription configuration, schedules,
  shard-to-group placement, schemas, producer IDs and auth. Subscription progress lives in data
  groups (6.5).

### 6.2 Write path and durability

- The leader of a data group appends each produce batch to the write-ahead log, together with
  its idempotency entries, and replicates it. In `replicated` groups every follower fsyncs before
  acknowledging to the leader, and an entry commits once a majority has fsynced it. **This rule
  never changes per topic.**
- Ack levels only change when the producer is answered: `quorum` after commit, `leader` after
  the leader's own fsync, `none` after the leader's in-memory append. A `leader` or `none` topic
  can lose a recently acked record if the leader fails, and the admin API states the window, but
  it can never cause a committed record of another topic to be lost.
- **Group commit**: one fsync covers every entry that arrived during the previous fsync, so the
  safe path is also the fast path.
- **The sequencer is always the data group.** Offsets for a topic-shard are assigned by the
  leader of the group hosting it, for every storage class.

### 6.3 Write-ahead log and the state stores

The write-ahead log is only for replication and recovery. Committed entries are applied to
per-node **state stores**, and the log is truncated independently.

- **Segment store**: each topic-shard has its own segment files: a fixed header with a format
  version, length-prefixed record batches, a CRC32C on every batch, and sparse offset and time
  indexes. Retention and compaction work per topic-shard on these files.
- **Subscription state store**: an embedded ordered key-value store per node holding ack floors,
  acked ranges, leases, attempt counts, cursors, broadcast member state, redelivery records, the
  **delay index** (keyed by due time, so the next due message is a range scan, not a memory
  table), the **per-key pending index** (5.8), producer sequence state, idempotency entries and
  transaction state.
- **Checkpoints.** Each node periodically fsyncs its segment store and state store and records
  the write-ahead log index they reflect. The log is truncated below the lowest checkpoint the
  group still needs. A follower too far behind is caught up with a snapshot: the segment files and
  a state-store checkpoint.
- **Trade-off, chosen deliberately.** Every byte is written twice: once to the log, once to
  segments. Pulsar's research report warns about exactly this double write. The alternative,
  using the shared log as topic storage, makes per-topic retention impossible because a shared
  log can only be trimmed from the front. Mitigations: segment writes are buffered and fsynced
  only at checkpoints, because the log already guarantees durability; the log is short-lived; and
  large payloads can later be written to segments directly with only a reference in the log.

### 6.4 Corruption and recovery

- Every log entry, segment batch, index page and checkpoint carries a checksum.
- Each replica persists, with every fsync, the highest log index it has acknowledged to the
  leader. On start it validates its log and segment tails. A damaged entry above that index was
  never acknowledged and is a torn write, so it is truncated. A damaged entry at or below it may
  be committed, so it is treated as corruption, never truncated as torn.
- **Protocol-aware recovery** (as in the CTRL design, FAST 2018): a replica that finds corruption
  in entries it acknowledged marks itself **recovering**. It may neither start an election nor
  grant its vote to anyone until it has repaired every corrupt entry from the current leader or
  a majority of replicas. If a majority of replicas are corrupt for the same entries, the group
  stops accepting writes and raises a critical alert rather than electing a damaged leader;
  recovery is then an operator action with a documented runbook.
- The modified election rule is model-checked (TLA+ or an equivalent) before M2 ships.

### 6.5 Subscription state and assignment

- **Assignment.** For per-shard ordering with shared distribution, the server assigns shards to
  members incrementally: only the shards that must move, move, and each move increases that
  shard's epoch (5.5). For exclusive distribution, failover moves the whole subscription to a
  standby member and increases the epoch of every shard. There is no stop-the-world barrier and no client-side assignor. Shared distribution with
  no or per-key ordering needs no assignment: any member may receive messages from any shard.
- **Per-message state** per subscription (per member under broadcast) per shard: an ack floor, a
  set of acked ranges above it, leases, attempt counts and redelivery records, all in the state
  store and replicated through the log.
- **Dispatch runs on the shard leader**, because it owns the per-message state. Followers can
  serve record bytes to members of cursor-style subscriptions (cumulative ack) in their own zone.
  Per-message subscriptions read through the leader.

### 6.6 Retention, caps and memory bounds

- Retention by time and size per topic. A segment is kept while any **non-suspended** durable
  subscription still owes messages in it, within that subscription's backlog limits (5.10).
- **Caps are enforced at admission.** Each topic and namespace has a hard storage cap. Producers
  are warned, then refused with an explicit, retryable "storage full" error. The broker never
  deletes a message a non-suspended subscription still owes.
- **State records never hit the cap.** Acks, nacks, leases and transaction markers have their
  own reserved space outside the cap, so consumers can always ack and free space. Dead-letter
  appends have a second reserve.
- **Memory bounds.** Resident memory per node is bounded by: in-flight leases, the cache sizes
  set in the node profile, and per-connection buffers. Backlog size, delayed messages, parked
  keys, distinct keys, idempotency entries, dispatch frontiers, debounce timers, per-key quota
  buckets and budget counters all live on disk behind fixed-size caches. The M1 exit bar tests
  each of these.
- **Progress checkpoints count against the namespace storage quota**, not the state-record
  reserve. Only changed checkpoints are replicated, and a subscription may lower the 64 KiB
  limit.

### 6.7 Storage classes (M4)

Per topic, changeable online, with one offset space and the data group as the sequencer:

- `local`: segments on replicated local disk. Lowest latency.
- `tiered`: sealed segments are uploaded to object storage and removed locally after a delay;
  reads of old data go to object storage.
- `object`: segment bytes go to object storage in batched objects shared across shards, then are
  compacted per shard. Higher produce latency, no cross-zone replication of payload bytes.

Backends: S3-compatible APIs and a local-directory backend for development and tests. Key-based
compaction is a per-topic option.

### 6.8 Zones

Nodes carry a zone label. Replicas of a group are spread across zones. Cursor-style consumers
fetch record bytes from a replica in their own zone. Cross-zone bytes are metered per topic
(7.5).

### 6.9 Formats and upgrades

- Every segment, log entry, state-store record, checkpoint and protocol message carries a format
  version from M1.
- Each release reads data written by the previous release, and upgrades run node by node with
  mixed versions in one cluster. A release may only drop an old format after a release that
  rewrites it in the background.
- Every release's test suite includes upgrading a data directory written by the previous release
  and continuing under load.
- M1 is a preview. Its data is upgradeable to M2, but it is not supported for production.

## 7. Platform features

### 7.1 Schema registry (M3)

- Per-topic schema with versions, stored in metadata. JSON Schema and Protobuf first; Avro later.
- Compatibility modes per topic: backward (default), forward, full, none. Registering an
  incompatible schema fails with a readable diff.
- Optional produce-time validation per topic; invalid records are rejected with the error,
  per record, as in 5.2.

### 7.2 Tenancy and auth (M2)

- Namespaces with quotas: produce and consume bytes per second, stored bytes, topics,
  subscriptions, connections, idempotency entries.
- API tokens scoped to namespace and topic-name prefixes with produce, consume and admin
  permissions. TLS for clients and mTLS between nodes.

### 7.3 Flow control

- Credit-based per connection, with per-topic and per-namespace limits. A throttled producer
  receives an explicit, retryable error with a suggested back-off. There is no cluster-wide stop.
- Bounded memory per shard and per connection; overflow throttles. Memory limits are absolute
  values from a node profile, validated at start, never percentages.

### 7.4 Observability

- Prometheus endpoint built in. Per subscription: backlog count and bytes, **oldest owed message
  age**, in flight, redeliveries, dead-letter rate, quarantines, skipped ranges, suspended state,
  per-key stalls. Per topic: bytes in, out, stored, cross-zone. Per node: memory against its
  bounds.
- **Message lookup** (M2): the `id` encodes topic-shard and offset, so `trib message get <id>`
  reads the record directly. It shows, for every subscription, the current state: pending,
  delayed until, in flight (member, since, attempt), acked, held, dead-lettered (with the
  dead-letter location) or skipped. A bounded recent-history ring per subscription, default one
  hour, shows the transitions with timestamps. Older acks show "acked" without a time, because
  ack state is stored as ranges.
- **Stuck report** (M2): per subscription, why it is not progressing: no consumers, all leases
  held, head-of-key or head-of-shard retries, held keys, delays, rate limit, throttling, schema
  failures, suspension, an open transaction holding the last stable offset.
- OpenTelemetry trace context travels in broker-managed headers, and the broker emits spans for
  produce, dispatch and ack (M2). Incoming `traceparent`, `tracestate` and `baggage` are kept byte
  for byte (5.14.10).
- **AI metrics** (M1 single node, M2 cluster): per pool, units granted, used, debt and overshoot;
  per priority band, wait time against its maximum; per fairness value, dwell time and in-flight;
  per subscription, superseded, cancelled, coalesced, throttled and paused counts; age-at-ack
  histograms and last-acked offset per key for freshness (D17).

### 7.5 Cost visibility

Per namespace and topic: bytes produced, delivered and stored by storage class, cross-zone bytes,
object-store requests, idempotency entries. Usage reported on ack (tokens, cost or custom units)
is aggregated by subscription, pool, tenant and any configured header labels, such as feature or
model (5.14.4). Exposed as metrics and through the admin API.

### 7.6 Data governance and AI data security

AI pipelines move personal data into prompts, embeddings and training sets, and regulation now
requires records of what happened. These features come from the data-pipelines research (D2,
D9 to D16) and the agents research (A14).

- **Server-stamped tenant** (D16, M2): an API token may be bound to a tenant. The broker stamps
  `trib-tenant` on every record that token produces and rejects a record whose client-supplied
  value differs. Tenant-scoped subscription tokens receive only their tenant's records, enforced
  by the broker, not by a client-side filter.
- **Provenance** (D14, M2): the broker-managed `trib-origin` header records the source topic,
  offset, producer, schema version and outbox origin. It survives relay, requeue, fallback
  routing, forks and transaction outputs, and it is queryable by key.
- **Audit** (A14, D12, M2): every namespace has an **access audit log**, a system topic with the
  `audit` topic profile. It records who produced, consumed, replayed, requeued, cancelled,
  paused or reconfigured what, by topic and offset range. It cannot be deleted or compacted
  before its retention, which defaults to one year and cannot be set below six months, the
  record-keeping period in the EU AI Act's Article 12 for high-risk systems. It is exportable.
  A topic may also set `audit: deliveries`, which adds every delivery attempt with consumer
  identity, outcome and reason, queryable by message ID.
  - **Complete**: an audit entry is written in the same commit as the state change it records
    (the lease, ack or configuration change) and shipped to the audit topic asynchronously and
    idempotently, so a crash cannot lose it.
  - **Bounded**: the audit topic has its own storage reserve and an alert at 80 percent. Its
    full-cap behaviour is a namespace setting: `fail-closed` (the default for `audit:
    deliveries`: dispatch for audited topics stops) or `fail-open` (entries beyond the cap are
    counted but not stored, and a critical alert fires).
  - **Pseudonymous**: keys, tenant values and consumer identities are stored as keyed hashes
    with a namespace secret, never as raw values or payloads, so erasure never needs to rewrite
    the audit log. The documentation states that the audit log is retained under the
    legal-obligation basis for record keeping.
- **Keyed deletes** (D2): `delete(key)` appends a **delete marker**. It is delivered in key
  order to every subscription that may see the key: it bypasses filters, sampling, coalescing,
  changed-field checks and backlog overflow, is auto-approved at gates, and is delivered
  at-least-once even to at-most-once subscriptions. It carries the producer's tenant, and
  tenant-scoped subscriptions receive only their own tenant's markers, so a marker never leaks
  another tenant's key.
- Markers are kept in a compact per-topic marker log until every subscription, including
  suspended ones, has received them or been deleted, so a suspension or retention cannot lose a
  delete.
- The broker then removes the key's earlier records from local segments and claim-check blobs
  (M3) and from tiered, object-storage and table copies (M4).
- **Erasure receipts** (D13): erasing a data subject deletes every key associated with it and
  every copy derived from those records. Copies are found through their provenance headers
  (`trib-origin`, `trib-source`, `trib-forked-from`, `trib-routed-from`): dead-letter copies,
  forks, fallback-routed copies, quarantine topics, shadow topics and claim-check blobs. The
  receipt lists each copy class and storage class processed, anything not yet processed, the
  subscriptions that received the subject's records, and whether each has acked the delete
  markers. Local copies and blobs are covered in M3, all storage classes in M4. In M5,
  per-subject crypto-shredding also makes backups unreadable.
- **Data-class labels** (D10, M3): schema fields can be labelled `pii`, `secret` or
  `user_content`. A topic may set a retention per class; after it passes, labelled fields are
  masked in place when segments are rewritten (M4).
- **Field-level access** (D11, M3): a token's scope lists the data classes it may read. The broker
  removes or masks other labelled fields before delivery, on every read path: dispatch, replay,
  dead letters, lookup, key reads, claim-check blob resolution and the MCP server. If a record cannot be parsed against its
  schema, labelled access fails closed.
- **Gated topics** (D15, M3): a topic may name a **gate subscription**, such as a PII or
  prompt-injection scanner. Records become visible to other subscriptions only after the gate
  approves them; rejected records go to a quarantine topic. Unordered subscriptions receive
  approved records as soon as they are approved. Per-key subscriptions wait per key, and
  per-shard subscriptions wait per shard, at the first record not yet approved, the same
  mechanism as the last stable offset in 5.6.
- The gate subscription is exempt from inactivity suspension and backlog overflow, and a stalled
  gate raises an alert. A record whose retention expires before approval goes to quarantine with
  reason "gate timeout", and ordered readers pass it as a recorded gap, so a stalled gate cannot
  block readers forever.
- **Shadow replay** (D9, M3): the `shadow-replay` profile replays a time range with a
  `trib-shadow` header, using a token with the `shadow` scope. That scope can produce only to
  topics flagged as shadow topics, and webhooks reach only allowlisted endpoints, so testing a new
  model against production traffic cannot cause production side effects.

### 7.7 Large payloads

Documents, images, audio and embeddings make large payloads an early need, so the claim-check
moves from M5 to M2 (I15, A10, D8).

- A topic sets `large_payload: reject` or `offload` with a threshold. Offloaded bodies go to an
  object-storage blob store behind a reference, and clients resolve them transparently.
- Blobs may have their own, shorter retention than the record, so prompt bodies can expire while
  the event survives. **Blob retention is absolute**: the blob is deleted when it passes, even if
  a lagging subscription still owes the record. After expiry, any read returns the metadata with
  an `expired` marker.
- Without a blob retention, a blob is **reference-counted** across the record and its copies
  (dead letters, routed copies, forks) and deleted when the last reference is gone. Blobs
  uploaded for a batch that was then rejected are found by a periodic reference scan and deleted.
- Blobs are resolved only through the broker, never by direct object-storage access, so
  field-level access (7.6) applies to them.
- The blob store uses the same backends as storage classes: S3-compatible APIs and a local
  directory for development.

## 8. Interfaces

### 8.1 Protocol and clients

- A native protocol in Protocol Buffers over gRPC: produce, producer sessions, pull, push with
  credits, ack, nack, extend, transactional ack, seek, profiles, schedules and admin.
- **An HTTP/JSON gateway with full parity** from M1: everything above, including nack, extend,
  seek and push over Server-Sent Events. `curl` works and serverless callers need no library.
- **Clients**: Go in M1; Python and TypeScript in M2; Java in M3. Each is generated from the
  protocol plus a thin layer for batching, sessions, ack flushing and handlers. Safe defaults
  everywhere: producer sequence numbers on, acks only after the handler returns, failures raised
  to the caller, never silent drops. When an application asks the client to add an idempotency
  key, the client creates it before the first attempt and reuses it on every retry.
- **Kafka protocol gateway** (M3): produce, fetch, metadata and consumer groups mapped onto
  topics and `event-stream` subscriptions, with a published compatibility matrix. Kafka
  transactions and compacted-topic semantics follow later and are listed as gaps until then.
- **Migration tools** (M3): import from Kafka with offsets preserved as positions, mirror a Kafka
  topic continuously for a dual-run period, and drain an SQS queue into a topic. The
  documentation includes a dual-run procedure.

### 8.2 Command-line tool

`trib` is the same binary as the server: `trib server`, `trib dev`, `trib apply -f <yaml>`,
`trib profile list|show|diff|rollout`, `trib topic create`, `trib sub create --profile <name>`,
`trib sub show|upgrade|resume <name>`, `trib sub stuck <name>`, `trib produce`, `trib consume`,
`trib message get <id>`, `trib dlq list|requeue`, `trib storage pinning <topic>`,
`trib schedule create|list`.

### 8.3 Local development

`trib dev` starts a single node with temporary storage and the HTTP gateway (and, from M3, the
admin page), with
the same semantics as a cluster. Test suites can embed the server in-process in Go.

## 9. Testing models

The exit bars in section 10 refer to these.

- **Fault-injecting filesystem.** All disk I/O goes through a filesystem interface. The test
  implementation, on a simulated crash, discards unsynced file data and unsynced directory
  entries and renames, can tear the last write at any byte, can reorder unsynced writes, and can
  return errors from fsync. A missing directory fsync must fail the suite.
- **Producer history check.** Every acknowledged record is present after recovery, exactly once
  per producer sequence and idempotency key, in per-shard order.
- **Consumer history check.** For each subscription: under at-least-once, no acked message is
  redelivered and every owed message is eventually delivered or dispositioned by policy; at most
  one ack is accepted per delivery token; per-key and per-shard order is never violated; under
  at-most-once, no message is delivered twice; under exactly-once, every input's outputs appear
  exactly once and no reader sees records of an aborted or open transaction.
- **Cluster fault suite** (from M2): network partitions, process pauses, kill -9, clock skew,
  disk corruption on one replica and on a majority, leader failover during transactions and
  during shard assignment changes. Both history checks run on every test.
- **AI dispatch checks**, added to the consumer history check: while capacity exceeds the overdue
  arrival rate, no message waits beyond `max_total_wait` plus one dispatch round, and cross-shard
  priority inversion stays within the stated bound; durable leases and parked batches survive
  leader elections without redelivery; a small tenant's dwell time beside a tenant with a million
  backlog stays within twice an idle system's; granted estimates never exceed the pool plus one
  chunk per dispatcher, including across coordinator failover, actual overshoot stays within the
  stated bound and is repaid, and a child never exceeds its parent; a pool-scope pause from a
  token without `pool-admin` never pauses the pool; cancelled, superseded and coalesced
  messages are never redelivered; cancel and supersede notices reach pull and push holders
  within one second; throttled nacks never consume attempts until `max_throttled` passes; delete
  markers are never dropped and never reach another tenant's subscription; every delivery
  attempt has an audit entry after any crash; ungated records never reach other subscriptions; fields a token may not read
  never appear on any read path.

## 11. Decided by the owner

- Build one platform that addresses the pains of existing streaming platforms and message queues
  in a single tool, based on research across existing systems including community reviews.
- It is for real users in production, so all milestones and their full test bars are in scope.
- Rewrite in Go; the TypeScript prototype is removed.
- The project is named **Tributary**: the repository, the local folder and all docs.
- Fully consumer-oriented: the consumer chooses pull or push, pub-sub, retry policy and delivery
  semantics, and everything is customizable through profiles.

## 12. Decided by the designer (Claude), open to the owner's override

- **Go**, accepted by the owner, for a single static binary, readable runtime, mature Raft and
  gRPC libraries and build speed. Rust was the alternative for tail latency.
- **Milestone order**: replication moves to M2, which is the first production release; M1 is a
  preview with upgradeable data. Exactly-once, webhooks, schema registry and the Kafka gateway
  move to M3 so they are built once, on the cluster.
- **Outbox relay in M3, not M2.** It produces through producer sessions and idempotency keys and
  belongs with producer transactions, which need the cluster's transaction coordinator. The
  review asked for M2; the key-ID field for crypto-shredding is reserved in M1 as asked.
- **Native protocol first, Kafka gateway in M3** rather than M5, as a migration bridge, without
  shaping the core around Kafka's partition model.
- **Write-ahead log plus state stores**, accepting the double write (6.3).
- **Fixed shard count with default 4 until M4.**
- **The settings model, the compatibility rules R1 to R24, and the built-in profile catalogue**,
  including dropping `fire-and-forget` (it overlapped `live-pubsub`) and renaming
  `durable-pubsub` to `broadcast` to discourage using it for service fan-out.
- **Defaults** that differ from revision 1: `start` is `earliest` for durable subscriptions; TTL
  expiry drops by default; `ordered-work-queue` retries 5 times up to 1 minute; the idempotency
  window is 15 minutes; backlog overflow dead-letters by default; inactive subscriptions are
  suspended after 3 days; departed broadcast members are removed after 1 hour; ephemeral
  subscriptions drop exhausted messages instead of creating dead-letter topics.
- **Profiles pin versions; built-ins are immutable.**
- **Message IDs encode location** and are not time-sortable.
- **Lease grants are not durable before dispatch under at-least-once** (5.6), trading a possible
  one-attempt undercount per failover for consume throughput.
- **Egress guard on by default for webhooks.**
- **AI scope and boundary.** Tributary takes the dispatch, quota, cancellation, checkpoint,
  stream, protocol and governance requirements from the AI research, and leaves step journaling,
  workflow versioning, sagas and agent memory to workflow engines (5.14.12).
- **Priority is now a goal**, implemented in the dispatcher with ageing, and constrained by R16
  and R18 so it never breaks per-key or per-shard order.
- **Claim-check moves from M5 to M2**, because multimodal AI payloads make it an early need.
- **Pool overshoot is bounded, not zero**, in a cluster: pools grant token leases in chunks to
  each dispatcher (5.14.4).
- **GenAI trace attributes wait** for the OpenTelemetry conventions to become stable.
- **Audit retention minimum of six months**, from the EU AI Act's Article 12 record-keeping
  period for high-risk systems, as reported by law-firm summaries in the research.
- **Apache-2.0 licence.** Binary and CLI `trib`; header prefix `trib-`; Go module path
  `github.com/nileshkr9919/tributary`.
