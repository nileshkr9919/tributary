# Classic brokers

Research date: 2026-10-19. Scope: RabbitMQ (classic queues, quorum queues, streams, AMQP 0-9-1, AMQP 1.0 in 4.x, MQTT), Apache ActiveMQ Classic and Artemis, with a short contrast against IBM MQ and ZeroMQ.

Coverage note: Reddit could not be read from this environment (www.reddit.com and old.reddit.com are blocked and search did not return Reddit pages). Community sentiment below comes from Hacker News, GitHub issues and discussions, the rabbitmq-users list, and engineering blogs. No Reddit quotes are used, and nothing here is invented; where a claim could not be checked it is marked as such.

## Architecture

**RabbitMQ.** Publishers send to an *exchange* (direct, fanout, topic, headers; 4.0 added a Local Random exchange), which routes to *queues* via *bindings*. The broker *pushes* deliveries to consumers; each channel sets a *prefetch* (QoS) that caps unacknowledged deliveries in flight. Consumers `ack`, `nack` or `reject` each delivery, with optional requeue. A queue can carry a *dead-letter exchange* (DLX) for rejected, expired or over-limit messages, per-queue and per-message *TTL*, and *length limits*. Priority is a classic-queue feature (and from 4.3 a strict 0-31 level feature on quorum queues) [11]. Delayed delivery is a separate *delayed-message exchange plugin* that stores timers in a single-node Mnesia table, is unreplicated, "doesn't really fit scenarios with a high number of delayed messages", and whose README now states "Team RabbitMQ no longer maintains this project" (repo archived) [16].

Queue types:
- *Classic queues*: one Erlang process per queue, "limited to a single CPU core on its hot code path" [12]. Historically replicated by *mirroring* (HA policies). Mirroring was deprecated in 3.x and "completely removed" in 4.0, so classic queues are now single-replica [9].
- *Quorum queues* (3.8+): Raft-replicated, leader plus followers, confirms only after majority replication, one shared write-ahead log per node, segment files and compaction on disk. Every message costs at least 32 bytes of in-memory index ("at least 1MB for every 30000 messages"), the WAL may hold up to 512 MiB in memory, the docs say to "overprovision disk space", throughput "tails off quite a bit" above five replicas, and the project advises "fewer than ~5000" queues per cluster. Not supported: exclusive queues, non-durable queues, global QoS. Since 4.0 the default `delivery-limit` is 20, after which messages are dead-lettered or dropped [11][9].
- *Streams* (3.9+): persistent, replicated, append-only log with non-destructive reads, offset/timestamp replay, size/age retention, super streams for partitioning, a dedicated binary protocol, and no DLX, TTL, priority or memory-alarm reaction. Streams "do not explicitly fsync", so an uncontrolled node shutdown can lose data on that node [13].

**Cluster and metadata.** Nodes form a cluster sharing metadata. Through 3.x metadata lived in *Mnesia*, whose replication "assumes that the system ... can afford to throw away all data on one side of a network partition"; the `pause_minority` / `autoheal` / `ignore` strategies were "by no means a fundamental solution and are difficult to reason about" [14]. 4.0 made the Raft-based *Khepri* store fully supported, 4.2 made it the default, and the 4.3 partitions guide says the Mnesia-era "Partition handling strategies ... were also removed"; the whole cluster now needs a majority of nodes reachable [10][14].

**Cross-cluster and backpressure.** *Federation* and *Shovel* move messages between clusters or brokers over AMQP (HN commenters call federation "the killer feature ... that NATS doesn't really have" [3]). Flow control is credit-based per connection, plus *memory* and *disk alarms*. The alarm threshold defaults to 40% of RAM in 3.x and 60% in 4.x; "the memory and disk alarms are cluster-wide; if one node goes over the limit then all nodes will block connections", consumer-only connections keep working, and for publishers that ignore the `connection.blocked` notification "publish operations will eventually time out or fail outright" [15]. The broker runs on *Erlang/OTP* (4.0 requires Erlang 26.2); each queue, channel and connection is a BEAM process.

**Protocols.** AMQP 0-9-1 is the native wire protocol. 4.0 made AMQP 1.0 "a core protocol that is always enabled" rather than a plugin; MQTT (3.1.1 and 5), STOMP, and the stream protocol are also served [9].

**ActiveMQ Artemis.** Artemis uses an *append-only journal* of pre-allocated fixed-size files with Linux AIO (falling back to NIO or memory-mapped), compaction, paging to disk under memory pressure, and "large messages are persisted outside the message journal"; a JDBC store exists but the file journal is recommended [18]. HA is active/passive: *shared store* (SAN; "naturally immune to split-brain") or *replication* (network copy to a backup, with an explicit split-brain warning and a ZooKeeper-based pluggable lock manager that requires at least three ZooKeeper nodes for isolation protection). On failover "the broker does not reproduce full server state", unwritten data is lost, and once-and-only-once needs duplicate detection plus transaction retry [17]. Artemis speaks Core, AMQP 1.0, OpenWire, MQTT, STOMP and HornetQ. In November 2025 the ActiveMQ PMC voted to make Artemis its own Apache top-level project, with ActiveMQ Classic continuing as a separate project [19].

**IBM MQ and ZeroMQ, for contrast.** IBM MQ is a licensed queue manager (priced per processor value unit / virtual core; reviewers cite roughly $277 per month per VPC and "learning and training cost ... is high") with strong transactional and mainframe integration [22]. ZeroMQ is a library, not a server: messaging goes "directly between senders and receivers without the need for a centralized broker" and it "does not provide built-in message reliability", so durability and delivery guarantees belong to the application [22].

## Strengths

- **Task queues and work distribution.** Push delivery with prefetch, per-message ack, DLX and TTL make retry and back-off topologies cheap to build. HN, 2024: "for anyone with less than a million users it's great"; another team "used it for a system with 100M+ users for our login systems" [3].
- **Routing flexibility.** Topic and headers exchanges, bindings and alternate exchanges let one publish fan out, filter or route without producer changes; one team left a Redis-backed queue because they "needed priorities and complex routing" [3].
- **RPC.** `reply_to` plus correlation ids and exclusive reply queues are first-class in every client library.
- **Operational simplicity for small teams.** A .NET team on HN: "RabbitMQ has been rock-solid. We never have to think about it, it's just been running for years." [21] Clustering via an Erlang cookie and `join_cluster` is easy to automate.
- **Protocol breadth.** AMQP 0-9-1, AMQP 1.0 (native in 4.x), MQTT 5, STOMP and streams in one broker; HN: "at least AMQP 1.0 is now supported", which lets clients move between brokers [3].
- **Mature release engineering.** "Besides a quality product the development/release process was very professional and mature" [3]. Streams give replay and "millions of messages per second" fan-out that older RabbitMQ lacked [3][13].
- **Artemis** offers a very fast local journal, JMS/Jakarta fit, and a wide protocol set for Java estates.

## Why people leave

- **To Postgres (or any RDBMS) for job queues.** Prequel replaced RabbitMQ with one table and `SELECT ... FOR UPDATE SKIP LOCKED`, netting "-580 lines of code"; their trigger was prefetch holding long jobs hostage [1]. HN agreed widely: "The best thing about using PostgreSQL for a queue is that you can benefit from transactions"; "Scaled much, much further than I would've guessed" [2]. The underlying driver is that a task queue wants pull semantics, visibility timeouts and transactional enqueue, none of which RabbitMQ's push model gives natively.
- **To SQS / cloud queues.** "the SQS visibility timeout model has in general been easier to reason about" [2]; "I wouldn't use RabbitMQ. I'd use SQS." [21]. Driver: zero ops, no memory alarms, no cluster to partition. Counter-driver cited: SQS's 12-hour unack limit and 15-minute delay cap.
- **To Kafka / Pulsar for streaming and fan-out.** Reasons given: "More services needed the same data" and queues "became larger, and scaling became increasingly difficult" [5]; "Kafka is extremely reliable, simple to cluster, battle tested" [21]; one long-time user left for Kafka, then Pulsar for selective acks [4]. Driver: replay, retention, partition-parallelism, consumer groups. Note the reverse flow exists too: a team went Kafka to RabbitMQ "in favor of (operational) simplicity and YAGNI" (StackShare, undated).
- **To NATS.** "RabbitMQ is a postal system, while NATS is a switchboard"; JetStream sourcing "has equivalent functionality to federation out of the box" [3]. Driver: single static binary, lightweight ops. No verified case study of a large production migration was found; Medium posts making that claim were inaccessible or lacked evidence.
- **To managed RabbitMQ rather than leaving.** ottonova moved to Amazon MQ because of the skills gap and because "data recovery was a challenge", accepting a 99.9% SLA [20]; another team moved the other way to EC2 after Amazon MQ maintenance windows "lost in-flight messages" (dev.to, undated).
- **Away from clustering while keeping Rabbit.** Several HN users fell back to single-node plus durable messages and backups after "split-brain scenarios and Mnesia database corruption" [4].

## Cost

- **Software.** RabbitMQ, ActiveMQ Classic and Artemis are free (MPL 2.0 / Apache 2.0). RabbitMQ community support windows are short: 4.0 ended 2025-04-15, 4.1 ended 2026-01-30, 4.2 ends 2026-07-31 [24]. Staying on an unsupported minor means no security backports, which pushes teams into frequent upgrades (each with breaking changes) or Broadcom support, whose core minimums are reported by resellers at 72 cores from April 2025 but could not be verified against Broadcom pricing [7]. IBM MQ is roughly $277/month per VPC per third-party listings [22].
- **Managed hosting.** CloudAMQP: free shared tier; dedicated single node from $50/month (Sassy Squirrel), 3-node clusters from $297/month (Big Bunny), up to $17,495/month for a 5-node Loud Lion [25]. Amazon MQ for RabbitMQ: a 3-node mq.m5.large cluster is about $703/month before traffic per AWS's own worked example; third parties round this to "$700/month before your first message" [8].
- **Operational experience.** G2 reviewers put self-managed RabbitMQ at about four months to implement with "high" perceived cost (small sample). HN consensus: it is cheap to run when queues stay short and consumers are healthy, and expensive when they are not; "it's the maintenance and debugging that soak up time, money, and tears" [21]. Running in Kubernetes "is possible but hard to admin" [3]; quorum queues are "disk I/O-heavy" and need fast storage [11]. Artemis is cheap on hardware (one journal) but HA requires a SAN or a ZooKeeper ensemble.

## Design lessons for a new platform

- **Keep:** exchange-style routing (topic patterns, headers, fanout) decoupled from storage. It is the single most-praised RabbitMQ feature and the one Kafka and NATS users miss.
- **Keep:** per-message ack/nack with requeue, dead-lettering and TTL as core primitives, not plugins. Add first-class *retry with back-off* and *scheduled/delayed delivery* so users never build DLX+TTL chains or depend on an archived plugin.
- **Make the log the only storage model.** One replicated append-only log per queue (Raft or similar) that serves both destructive "queue" reads and non-destructive "stream" reads with offsets. RabbitMQ's three queue types with three feature matrices is the clearest lesson of what not to do.
- **Consensus from day one, no partition "strategies".** Majority-based metadata and data replication; no mode where the operator must pick between availability and data loss. Document the exact behaviour of a minority side (reject writes, serve reads from replicated data).
- **Backpressure per queue and per producer, never a global stop switch.** Replace the memory alarm with credit-based flow control, bounded per-queue memory, spill-to-disk by default, and an explicit error (not a hang) when a producer is throttled.
- **Deep backlogs must be boring.** No per-message in-memory index; a 100M-message backlog should cost disk, not RAM, and should not slow the node. Treat "consumer down for a weekend" as the normal case.
- **Scale a single queue across cores and nodes.** Partitioned queues with key-based ordering, so users are not told that a hot queue is "an anti-pattern".
- **Pull with leases as the default consumer model** (visibility-timeout style), with push as an option. Prefetch-holding-long-jobs-hostage, head-of-line requeue and channel-wide ack timeouts all stem from push-plus-prefetch.
- **Ordering guarantees stated per partition/key** and preserved across redelivery and consumer failover; single-active-consumer should be a mode, not the only way to get order.
- **Large payloads:** chunked frames or built-in claim-check to object storage, with limits enforced before buffering (see CVE-2026-67235).
- **Operability:** Prometheus-native metrics with no in-broker stats database; metadata operations (100k bindings) that are O(1)-ish; rolling upgrades across minor versions; and a runtime/language the median on-call engineer can read and profile.
- **Compatibility and governance:** speak AMQP 1.0 and MQTT 5 on the wire so existing clients work; publish long community support windows and a stable semver policy; avoid a single-vendor stewardship story that makes users ask "I hope they will remain unaffected".
- **From Artemis:** keep the fast pre-allocated journal and large-message side store, but do not ship active/passive HA that needs a SAN or ZooKeeper.
